Hindsight

N coding agents, N sandboxes, but every command that every agent runs identically executes exactly once across the fleet — keyed on git's own Merkle hash of the live workspace, served as a verified replay. Not a prediction. A receipt.

Revision — the sweep changed the target

Same product, but aim it at the cold start, not at general state sharing.

Rev 1 told you the value was in skipping expensive execution — test suites, builds. I re-measured against sealed-corpus/replay-A (25 SWE-bench tasks, each attempted by 3–26 independent agents, 11,687 commands) and that framing is wrong in a specific, fixable way.

The first expensive command lands at median step 18 — long after agents have diverged. By the time anyone runs pytest, the trees differ, because the agent's own edit is what makes it a different agent. Its pre-verification state is unique by construction.

But overlap is real and it is front-loaded, which is the thing to build on.

Where I disagree with my own sub-agent — say the right version

One sweep reported zero cross-agent hits on expensive commands. I get 10.4% (53/509). The difference is the key: that sweep matched on (tree state, command); I matched on command only. Both are true and the gap between them is the honest finding — command-level overlap on expensive work is ~10%, but state-matched overlap is ~0, because trees have already diverged by step 18.

This also corrects rev 1's 23.9% figure: that measurement was state-free too. It is a real number for read-only probes, where state-insensitivity is defensible. It is not a licence to cache a test run. Never serve a mutating or expensive command on a command-only key.

A limitation to volunteer before anyone finds it

This corpus starts from a pre-built container. It contains no uv sync, no pip install, no image build — so it cannot measure the setup convoy, in either direction. The structural claim that five worktrees all run the same install at a byte-identical HEAD is sound reasoning, not a measured result here. Say that on stage. It costs you nothing and it is exactly the kind of thing a YC judge tests for.

The mechanism — verified live, this session

git already computes the hash you couldn't design

lucid-thoughts.md asks for a key where "hash a is comparable to hash b the same way state a and b are." A side-index write-tree gives you the exact-match half of that for free:

# NOT this — a throwaway index re-stats every file, 220ms warm / 580ms cold
# SIDE=$(mktemp -u)

# This — a PERSISTENT side index, pre-warmed once per worktree
SIDE=.git/hp-index
GIT_INDEX_FILE=$SIDE git add -A
GIT_INDEX_FILE=$SIDE git write-tree   # → 4cf8231d1600273ab5…

I ran it twice on your skunk-works checkout: identical hash both times, and git status confirms the real index is untouched (M index.html, M technical-report.html still staged as they were). It is a true Merkle hash of the live workspace and it returns the same value when a workspace revisits a prior state.

Timing correction — rev 1 said ~10–40 ms

That figure only holds for a persistent, warm index. Measured on skunk-works just now: throwaway mktemp index 580 ms cold / 220 ms warm; persistent .git/hp-index 220 ms cold / 20–30 ms warm. On an 11k-file repo the throwaway version was measured at 1250–1740 ms — a visible hang in the hook path. Use the persistent index, and pre-warm it on every worktree during setup, not just the presenting one.

Claude Code's PreToolUse hook returns updatedInput, so a hit rewrites the command into cat /tmp/hp/<key> and the model receives a clean, non-error tool result in about a millisecond. That is the entire integration surface.

Your best slide is a negative result

The isomorphic hash is ill-posed — and you can prove it

You've been stuck on making hashes comparable the way states are. That object cannot exist as one artifact: comparability requires a lossy projection, cache-safety requires injectivity, and the two are opposed. On your own numstat representation, three trees containing x = 99, x = -7, and import os; os.system("rm -rf /") all hash to the same state_sha256.

The "just use embeddings" fix is self-refuting: a key loose enough to make agent-1's edit collide with agent-2's edit then serves agent-2 a test result produced by different code — and telling those two edits apart is the entire reason the suite is running. You already measured this from the other side: ρ(surface similarity, |outcome gap|) = −0.252, p = 8.3e-77.

So: exact Merkle key for serving, similarity only for advisory notes. Present the impossibility as a finding, not a gap. It is the most senior thing you can say on stage.

Nobody ships this

Conductor, Vibe Kanban, Claude Squad, Crystal, Emdash, Baton, Paseo — every parallel-agent tool isolates agents. Zero npm or pip packages memoize agent tool calls across agents. The fan-out orchestration layer exists and is crowded; the shared-execution layer underneath it is empty.

Your own repo has the one validated instance of the thesis: ONEIROLOGY_MODEL.md:158-161 — two agent instances on different hosts, knowledge passed through a written artifact (INHERITED_FINDINGS.md), and the second agent did not repeat the first's dead ends. The mechanism was a markdown file, not a hash. That both proves the value and suggests the hard part you've been stuck on may be unnecessary.

Sixty seconds

ProblemFive agents on one bug, five sandboxes. They all install the same dependencies. They all run the same failing test to reproduce it. They all read the same six files. You pay five times for one piece of information, every single time.

What it isThis is Hindsight. Every command is keyed on git's own hash of the workspace. If a peer already ran it at the same tree, you get their recorded result back instead of running it.

DemoLeft, five agents, no sharing. Right, same five, same bug, sharing. Watch the bottom counter — that's execution-seconds deleted. Not saved. Deleted. Work that was paid for once and provably not paid for again.

The guaranteeEvery served result is a verified replay of a real execution, and I re-run all of them in the background to check. Thirty-one served, thirty-one verified, zero divergent. There's no model here. Nothing is predicted.

The findingAcross twenty-five SWE-bench tasks with up to twenty-six agents each, overlap is twenty-six percent in the first three commands and eleven percent after step ten. Agents start identical and diverge. Everything worth sharing happens early.

Why believe youI built a world model for this first. I gated it, four of six heads failed, and I killed a three-hundred-and-forty-dollar experiment for eighteen. The cache is what survived.

The honesty rule

Subtraction, not speedup

Your standing order at DIRECTIONS.md:191 is "NEVER: race wall-clock incumbents." The way to obey it and still show a clock: don't claim a speedup, claim a deletion. Execution-seconds deleted is arithmetic over measured durations, not a benchmark — it is the sum of real times that were really spent and really not spent again. Nobody can argue with a subtraction.

Show n=1 live as illustration and a pre-recorded n=5 as the evidence, and say out loud which is which.

Risks, ranked

  • THE GITIGNORE HOLE — the only thing that can make Hindsight wrong rather than silent. git add -A respects .gitignore, so .venv is not in the tree. Verified: two checkouts with different .venv contents produce an identical tree hash. That falsifies "never wrong when it answers" — the entire pitch. Fix before anything else touches the daemon: fold an environment fingerprint into the key — sha256(python -V, uname -m, hash of lockfile / pip freeze). This goes from theoretical to probable the moment a second laptop joins, because two machines genuinely do have different dependency state. If you skip exactly one item on this page, it must not be this one.
  • You serve cached uv sync stdout and agent-2 has no .venv. The next pytest explodes with ModuleNotFoundError, live, and the whole thing reads as theater. Most likely on-stage death, because install commands are your best hit and the naive build caches only text. Guard: the H+3.5 artifact clone. Non-negotiable.
  • Hit rate is zero on the live fleet. Guard: the H+3.0 checkpoint, before any UI, with the replay-mode fallback ready.
  • Greptile hosts this, and their public line is “agents should just run the code.” You agree — you never replace execution, you replay a peer's and verify it. Have the sentence ready: “I agree, run the code. I'm telling agent five what happened when agent two already ran it.”
  • “Shouldn't you diversify agents instead of duplicating them?” The sharpest question you'll get, and your own five-agent research run backs the challenger: 150 arXiv works across 6 reports, 7 shared — redundancy 1.06×. Answer: diversified agents share nothing by design, and best-of-N on one task is not diversification, it's a race. Hindsight pays in the race, not in the survey.
  • A cached read is still an LLM turn. Returning a cached grep saves the exec, not the turn. Say “execution-seconds,” never “turns,” unless you inject proactively into context.
  • Don't bolt the old demo on for visual weight. stage0a-rerun-report.json shows any_named_path_movement at 0.9496 where the always-none constant also scores 0.9496. Hindsight containing no model is the cleanest defence you have.
